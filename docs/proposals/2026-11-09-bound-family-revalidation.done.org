#+TITLE: Bound family revalidation by version count
#+DATE: 2026-11-09

Status: *done* (2026-11-10) · found by the review in
[[file:2026-11-08-write-path-storage-audit.org::*Independent review][the write path and storage audit]]

* Problem

Operation-local family observations made write analysis reusable
([[https://github.com/rails-to-cosmos/org-glance/commit/113814b][113814b]]).  A
reuse revalidates the observation by re-stating every path it recorded, two per
version plus the =versions= root and the legacy blob —
=src/data/org-glance-version.el= line 339 at
[[https://github.com/rails-to-cosmos/org-glance/commit/e464239][e464239]].  The check is therefore linear in a
family's version count.

| Versions | Proof paths | =current-p= ms | Observe reuse ms |
|----------+-------------+----------------+------------------|
|        8 |          18 |           0.92 |             0.95 |
|       32 |          66 |           3.58 |             3.49 |
|      128 |         258 |          13.78 |            12.28 |
|      512 |        1026 |          54.45 |            50.16 |

=~/sync/views= holds one family of 514 versions against a runner-up of 33.
The original measurement puts one reuse check at about 54 ms; the implementation
comparison below measures 49 ms.  =graph:add= performs one such check when
writing a full headline to an existing ID.  Ordinary interactive capture and
duplication write fresh IDs and reuse a one-version family.  Deep-family reuse
is exercised by API callers, including migration of changed existing IDs,
tests, benchmarks and plugins.  Material open and save
perform fresh observations and zero reuse checks.

Reuse beats the walk it replaced, which read and parsed the same files.  The gap
is the gate.  =virtual-save-family-work-contract= exercises depths 1, 8 and 32
and asserts call counts, which are constant in V, so a revalidation cost linear
in V stays green.  Depth 32 measures 3.58 ms, an order of magnitude below the
live store's deepest family, so the ladder's top rung hides it.

* Design

1. *Extend the depth ladder to 512.*  =virtual-save-family-work-contract= gains
   a 512-version case.  The existing count assertions carry over unchanged.
2. *Assert the stat count.*  A contract counts =file-attributes= calls inside
   one =graph:add= reuse and bounds them independently of the version count.  Counting
   is deterministic, so this is a work-counter oracle in the project's existing
   style.
3. *Record the ceiling.*  =docs/invariants.org= gains the measured revalidation
   table under the write-path contracts, so a later change compares against it.
4. *Revalidate against the frontier.*  An observation's proof records the
   =versions= root's own stamps and the entries it listed.  A directory's mtime
   advances when a child is added or removed, so comparing the root's stamp plus
   the inventory it yielded detects published and retired versions in constant
   work.  Per-version stamps then guard only the versions an operation actually
   read, which for a save is its selected leaf and the structural leaves it
   publishes against.
5. *Keep full proof for the repair path.*  A reindex or an integrity pass asks
   for the exhaustive comparison; a read and a save ask for the frontier one.
   The exhaustive form stays as the explicit argument.

Item 4 is the behavioral change and needs its own case: a version directory
rewritten in place without touching the root, which the per-version stamps catch
today and the frontier check would miss for a version the operation never read.
Invariant 41 makes directory inventories the search authority, and a version's
payload is immutable once published (invariant 40), so an in-place rewrite of a
published version is already outside the contract.  The case belongs in the
proposal's test set to pin that reading.

The frontier check is weaker than the audit's own item 4, the persistent
generation counter, and cheaper to adopt: it reads stamps the filesystem already
maintains, so no independent writer has to participate.

* LOC estimate

Roughly 60 lines of source and 70 of tests.  Items 1 through 3 are about 30
test lines and 2 documentation lines on their own, and stand alone if item 4 is
deferred.

* Risk

Items 1 through 3 are measurement and carry none; they turn an unbounded cost
into a visible one.  Item 4 narrows what a reuse revalidates, so a stale
observation becomes possible where a published version is mutated in place
against invariant 40.  Taking items 1 through 3 first makes item 4's effect
measurable before it ships.

* Method

Depth table built by repeated =graph:add= on one id, timing
=version--observation-current-p= over 20 iterations and =version:observe= over 5
within one source context, Linux, Emacs 31.1.90.  Live family counts from =find
-mindepth 4 -maxdepth 4= over =~/sync/views=, read-only.

* Implementation

Ordinary operation reuse checks the versions directory, legacy source and each
structural leaf's envelope and payload.  One leaf requires four
=file-attributes= calls, independently of ancestry depth.  Concurrent leaves
add two stamps each.  The initial observation records structural leaves with a
hash index of parent IDs.  Frontier proofs are built from those leaves and
recorded stamps on first reuse; reuse never walks history.  Supplied inventories still compare with the retained inventory.  Symlink sources force a fresh observation.

The full proof remains available through =version:observe='s explicit
=exhaustive= argument; =graph:reindex= enables exhaustive revalidation throughout
its operation.  A fresh observation reads the complete family in either mode.
Selected source payloads retain their separate identity and digest guards.

The 512-version material fixture publishes immutable snapshots and reconciles
once before opening the editor.  Its work contract retains one parse and two
fresh observations per save.  =graph-add-family-revalidation-work-contract=
requires one successful reuse and four stat calls per add at depths 1, 8, 32
and 512; the direct reuse contract bounds the same depths.  Historical in-place
corruption remains visible to exhaustive repair and the next fresh observation.

Publication, content writes, deletion, cache projection, current-version reads
and pruning consume the observation's stored leaves.  Candidate selection
accepts those leaves explicitly.  =graph-write-analysis-work-contract= requires
one leaf computation per fresh observation across insertion and reindex.

Measured baseline and implementation values are recorded in
[[file:../invariants.org::*Write-path analysis contracts][Write-path analysis contracts]].

** Findings

1. *The save-path stat assertion is vacuous.*  The 512-version fixture of
   =virtual-save-family-work-contract= records zero checks and zero stats at
   depths 1 and 32, so =(<= stats (* 4 checks))= in
   =test/test-material-virtual.el= line 523 holds as =0 <= 0=.  Pin the
   four-stat ceiling at depth 512 on the =graph:add= path
   (=versioned-write-observes-family-once= or
   =graph-write-analysis-work-contract=) and drop the save assertion.
   =family-revalidation-work-contract= stands.
2. *The save premise is wrong.*  Saves perform no reuse check, so the 109 ms per
   save in [[*Problem][Problem]] never existed and this change leaves saves
   unchanged.  The gain is about 49 ms per =graph:add= / =graph:insert= on the
   514-version family.  Correct the save claims in
   [[file:../invariants.org::*Write-path analysis contracts][Write-path analysis
   contracts]], in [[*Implementation][Implementation]] and in
   [[file:2026-11-08-write-path-storage-audit.org::*Findings][the write-path
   audit's findings]]; the =CHANGELOG.org= bullet names the internal
   =org-glance-version:observe= and should name adds, captures and table or
   relation edits on long-history headlines.
3. *Invariant 41 lacks the narrowed trust rule.*  Reuse trusts unread ancestors
   through invariant 40's immutability; only reindex compares every stamp.
   Invariant 41 in [[file:../invariants.org][invariants]] and =CLAUDE.md= still
   read "revalidate source identity and mutation stamps" and owe one line.
4. *Leaves are recomputed beside a held observation.*  The observation now
   stores =leaves=; =src/data/org-glance-graph.el= lines 837, 887 and 1030 and
   =src/data/org-glance-cache.el= line 662 call =version:leaves= on a history
   whose observation is in hand and should read
   =version-observation:leaves=.
5. *Index placement.*  The new Done bullet in [[file:../index.org][the docs
   index]] precedes the "Newest first." line.
6. *Reindex delta accepted as noise.*  The paired delta is +22.6 ms (95% CI
   +6.5…+39.0 ms); the identical-code control widens it to −6.8…+45.3 ms.
   Reindex stats are unchanged under exhaustive revalidation, and the new
   =leaves= pass is O(V), replacing an O(V²) =member= scan.

Findings 1 and 2 block the commit; 3 and 4 belong to the same pass.

** Frontier soundness

- Added and retired event directories change the =versions= root stamp (size,
  mtime, ctime, inode); the previous proof also relied on that stamp alone for
  additions.
- A legacy-root leaf stats an absent =headline-dir/meta.json= and compares nil
  with nil.
- The =reusable= flag keeps symlink sources reading fresh at any depth.
- The memoized frontier is safe because mutation drops the observation.
