#+TITLE: Nonblocking cache reconciliation
#+DATE: 2026-10-12

Status: *done*

* Problem

Graph construction ran a complete immutable-family cache refresh on the Emacs
caller thread.  The session timer then ran the complete reconciliation every
second, even when the persisted inventory proof was current.  Large stores
therefore delayed startup and could repeatedly freeze an otherwise open Emacs.

* Decision

Startup and the session timer queue one cache refresh in an isolated batch
Emacs process. One graph has at most one active process, and automatic
steady-state requests are limited to one per minute.  Startup work leaves the
first post-open request due, allowing a Git update that lands immediately after
startup to queue its own reconciliation. Cache-backed UI reads continue from
the last committed SQLite projection while reconciliation runs. They never
request a census, History fold, or cache transaction.

An external relay fold remains a synchronous publication boundary.  Its
bounded notification work and inventory reconciliation complete before the
caller observes the relayed write.  Local family publication retains its
synchronous SQLite commit.

The explicit =org-glance-cache:refresh= and
=org-glance-cache:reconcile-inventory= functions remain synchronous maintenance
operations.

* Executable contract

- =graph-open-queues-cache-refresh-off-caller-thread= proves graph construction
  queues work before cached rows are read.
- =cache-refresh-async-uses-an-isolated-emacs-process= proves automatic work
  crosses the process boundary instead of using an Emacs Lisp thread.
- =cache-refresh-batch-does-not-queue-another-worker= prevents recursive workers.
- =cache-refresh-process-commits-across-the-process-boundary= verifies the real
  worker's committed projection.
- =cache-worker-finds-a-package-upgraded-in-place= keeps a live session able to
  launch a worker after its loaded package directory is replaced.
- =table-visit-builds-its-palette-from-cache-rows= and
  =table-property-column-uses-the-row-cache-only= keep a warm tagged Table on
  its committed Row and property projections.
- =startup-refresh-leaves-first-read-due= proves startup cannot hide a Git
  update behind the steady-state throttle.
- =inventory-tick-skips-a-proven-current-store= proves the timer does not repeat
  a proven census.
- =explicit-refresh-detects-after-nonblocking-read= proves explicit maintenance
  still discovers a relay-free Snapshot.
- The external-fold tests retain immediate relay visibility.

* Verification

- =eask recompile=
- focused cache/process/material-read regression sets
- =make test= (502 tests)

On the real 7,099-directory =~/sync/views= store, a forced-stale synchronous
startup exceeded the 120-second measurement cap. The asynchronous caller path
returned in 437 ms. At 1,000 families, the isolated worker launched in 1.5 ms
p50 and completed in 3.48 s p50 while foreground committed-projection probes
remained below 83 ms p50. The census remains optimization work; it cannot
occupy the interactive Emacs thread.

The 448-Row =alberblanc= Table with its saved property column rendered in
0.367 seconds after [[https://github.com/rails-to-cosmos/org-glance/commit/eff816c][eff816c]], down from a run exceeding 30 seconds. The action
benchmark also measures the full Table entrypoint and rejects any census,
History read, reconciliation request, or cache transaction.
